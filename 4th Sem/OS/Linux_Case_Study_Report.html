Chapter 1

Introduction

Linux is a Unix-like operating-system kernel that provides the core mechanisms needed to run processes, manage memory, access files, communicate between programs, and control hardware. A complete Linux system combines this kernel with user-space libraries, utilities, services, shells and applications. The kernel remains the privileged component that mediates access to the processor, memory and devices [1], [2].

The design is commonly described as monolithic because major services such as scheduling, memory management, networking and file systems execute in kernel mode. Linux is also modular. Functionality such as many device drivers and file systems can be compiled as loadable kernel modules and inserted or removed when required [1], [3].

Chapter 2

History

Linux began in 1991 when Linus Torvalds started a small kernel for Intel 80386 computers. The early project borrowed the Unix programming model and was developed in public with contributions distributed through Internet mailing lists and source archives. Its later adoption of the GNU General Public License made the source available for study, modification and redistribution under that license [1], [2].

The kernel grew alongside the GNU compiler, C library, shell and utilities, producing complete GNU/Linux systems distributed by projects and companies. During the 1990s Linux expanded from a personal-computer kernel into a portable system supporting servers, multiprocessor machines and many processor architectures. Modular drivers, networking, virtual memory and file-system support improved quickly because developers could contribute changes for particular hardware and workloads [1].

Linux development now uses a distributed version-control workflow centered on the upstream kernel tree. Subsystem maintainers review changes for areas such as networking, memory management, architecture support, storage and drivers before changes reach the mainline kernel. Stable and long-term-support branches then receive selected fixes. This organization allows a large codebase to evolve while keeping subsystem ownership clear.

The practical importance of Linux comes from reuse of the same kernel concepts across very different systems. Linux is used in servers, cloud platforms, supercomputers, embedded devices and Android-based systems. The hardware and user interfaces differ, but the kernel still performs the same central operating-system tasks: protection, resource allocation, abstraction and controlled sharing [1], [2].

The history also explains several present-day design choices. Compatibility with Unix and POSIX applications shaped process, file and permission interfaces, while continuous support for new hardware encouraged loadable modules and common driver frameworks [2], [9].

Chapter 3

Kernel Modules

A loadable kernel module is object code that can be linked into a running kernel when its functionality is needed. Typical modules implement device drivers, file systems, network protocols or other kernel extensions. This keeps the base kernel smaller and avoids rebuilding or rebooting the system for every optional component [1], [3].

Modules run in kernel mode and therefore have the same privilege as built-in kernel code. A faulty module can corrupt kernel memory or crash the system, so module code must follow kernel APIs and synchronization rules. External modules are normally built against the configuration and headers of the target kernel. The Linux kbuild system records symbol and version information needed to link the module correctly [3].

The commands lsmod, modinfo, modprobe and rmmod are common administration tools. lsmod lists loaded modules, modinfo displays metadata, modprobe loads a module together with dependencies, and rmmod requests removal. modprobe is usually preferred over insmod for normal administration because it understands dependency information [3].

3

3.1 Module structure, symbols and safety

A simple module has an initialization routine and an exit routine. The initialization path allocates resources and registers the module's services with the relevant kernel subsystem. The exit path reverses those actions so no device, timer, memory object or callback remains after removal. Kernel modules do not use the normal user-space C library; they use interfaces exported by the kernel [3].

The kernel maintains a symbol table for functions and data that modules may use. EXPORT_SYMBOL and related mechanisms make selected kernel symbols available to modules. Module dependency metadata allows tools to load prerequisite modules first. The kernel can also enforce signature policies so only accepted modules are loaded on systems configured for signed modules.

Synchronization is essential because module callbacks may execute concurrently on several CPUs or in interrupt context. Depending on the context, kernel code uses spinlocks, mutexes, atomic operations, wait queues and RCU-style techniques. A module must also respect reference counts. It should not be unloaded while some kernel object can still call into its code [1], [3].

Modules are therefore a compromise between flexibility and risk. They let Linux add hardware support and services at run time, but they are not isolated like user processes. A defect has system-wide consequences because module code shares the kernel address space.

Key point. Linux is monolithic in privilege level, but modular in construction. A module becomes part of the running kernel once it is loaded.

Chapter 4

Process Management and Scheduling Approaches

Linux represents each schedulable task with a kernel task structure that stores identifiers, state, scheduling information, memory references, open-file references and other execution context. A process can create another process with fork() or related clone operations, while exec replaces the current process image with a new program. wait-family system calls allow a parent to collect a child's termination status [1], [8].

Tasks move between runnable, sleeping, stopped and terminated states. A task that waits for I/O normally sleeps instead of occupying a CPU. When the event completes, the kernel wakes the task and makes it eligible to run. This separation between runnable and blocked tasks is basic to efficient multiprogramming [1].

Linux supports multiple scheduling classes. Normal interactive and batch work uses the fair scheduling class, while real-time policies such as SCHED_FIFO and SCHED_RR are available for tasks that need stricter priority behavior. The scheduler chooses among runnable tasks and also decides which CPU should run a task on multiprocessor systems [1], [4], [9].

5

4.1 Scheduling, priorities and context switching

The fair scheduler is designed to divide CPU time among runnable tasks while considering task weight or nice value. Classic CFS descriptions use virtual runtime to approximate an ideal processor that shares time continuously. The kernel selects the task that has received comparatively less weighted service. This gives normal workloads fairness without a fixed round-robin quantum [4].

Real-time policies use static priorities above normal tasks. SCHED_FIFO allows a runnable real-time task to continue until it blocks, yields or is preempted by a higher-priority real-time task. SCHED_RR adds a time slice among tasks at the same priority. Because a badly configured real-time task can starve ordinary work, these policies require administrative care [1], [9].

Table 1. Process states and scheduler meaning
StateMeaning for scheduling
Running / runnableEligible for CPU time; one task per CPU is actually executing.
Interruptible sleepWaiting for an event and can be awakened by signals.
Uninterruptible sleepWaiting for a kernel event where normal signal wake-up is deferred.
Stopped / tracedExecution intentionally suspended.
ZombieExecution ended; exit status remains until the parent waits.

A context switch saves the CPU state of the outgoing task and restores the state of the incoming task. The scheduler also works with load balancing so runnable work can move between CPUs. Affinity controls can restrict a task to selected CPUs, which can be useful for performance isolation or hardware locality [1].

Chapter 5

Inter-process Communication

Processes normally have separate virtual address spaces, so Linux provides IPC mechanisms for controlled communication and synchronization. The right mechanism depends on whether processes need a byte stream, discrete messages, shared data, event notification or communication across a network [1], [8].

Table 2. Main Linux IPC mechanisms
MechanismTypical useImportant property
Pipe / FIFOProducer-consumer byte streamsKernel-buffered stream; pipe is commonly related processes, FIFO has a name.
SignalAsynchronous event notificationSmall notification with limited payload.
Shared memoryHigh-volume local data exchangeProcesses map the same physical memory; synchronization is separate.
SemaphoreSynchronizationRepresents counts or resource availability.
Message queueDiscrete messagesKernel stores message boundaries and queue state.
SocketLocal or network communicationUniform endpoint API for Unix-domain and Internet protocols.

Anonymous pipes are created with pipe() and are often inherited across fork(). One process writes bytes and another reads them. Named pipes, or FIFOs, provide similar stream semantics through a file-system name. Pipes are simple and naturally support shell pipelines such as producer | consumer [8].

Signals notify a process that an event occurred. Examples include SIGINT from an interactive interrupt and SIGCHLD when a child changes state. Signals are useful for events, but they do not replace a structured data channel [8].

7

5.1 Shared memory, semaphores, queues and sockets

Shared memory is usually the fastest local IPC method for large data because communicating processes access the same mapped pages instead of copying each message through a kernel buffer. The tradeoff is synchronization. Processes must use semaphores, process-shared mutexes, atomic operations or another protocol to prevent races while updating shared objects [1], [8].

System V IPC provides shared-memory segments, semaphore sets and message queues. POSIX defines related shared-memory and message-queue interfaces. Message queues preserve message boundaries and allow the kernel to hold messages until a receiver reads them. Semaphores provide counters that can block a task when a resource is not available [8], [10].

Sockets extend the communication model. Unix-domain sockets communicate efficiently between local processes and can transfer credentials or file descriptors. Internet-domain sockets use protocols such as TCP or UDP and can communicate between different machines. The same read/write style of programming is therefore available for many local and network designs [8].

Linux IPC is closely tied to scheduling. A blocking read, semaphore wait or message receive can put a task to sleep. When data or a synchronization event becomes available, the kernel wakes an eligible waiter. This avoids busy waiting and lets the processor run other tasks while communication is pending [1].

Selection rule. Use pipes or sockets for streams, queues for discrete messages, shared memory for large shared data, and semaphores or mutexes for synchronization.

Memory Management Approaches

Linux gives each process a virtual address space. The CPU's memory-management unit translates virtual addresses through page tables to physical memory. Virtual memory isolates processes, supports protection bits and lets the kernel place pages in physical memory independently of the addresses used by programs [1], [5].

Process virtual address
↓
Page-table translation
↓
Physical page frame
↓
RAM or mapped storage
Figure 4. Virtual memory address translation

A process address space contains regions such as executable code, data, heap, shared libraries, stack and memory-mapped files. The mmap interface can map files or anonymous memory into that space. Page permissions control whether a mapping may be read, written or executed. Invalid or disallowed accesses generate a page fault that the kernel handles or reports to the process [1], [8].

Linux uses demand paging. A page does not always need a physical frame until it is first accessed. A page fault can allocate a zero-filled anonymous page, bring file data into the page cache, or perform copy-on-write after fork(). Copy-on-write allows parent and child to share unchanged pages until one process writes to them [1], [5].

9

6.1 Physical allocation, reclaim and swapping

The kernel manages physical memory in page-sized units and groups free pages so contiguous regions can be allocated when necessary. Higher-level allocators provide efficient storage for frequently created kernel objects. Linux also tracks memory by NUMA node and zone on systems where access cost or hardware constraints differ [5].

Unused RAM is valuable as a cache. File data read from storage is normally kept in the page cache so later access can avoid another device read. When memory pressure increases, the kernel reclaims pages that can be dropped or written back. Clean file-backed pages can often be discarded because their contents still exist on storage. Dirty pages must be written before they can be reclaimed [1], [5].

Anonymous memory may be moved to swap space when swapping is configured. The kernel attempts to balance the working sets of active processes with cache and reclaim needs. If the system cannot free enough memory, the out-of-memory mechanism may select a process for termination so the system can recover [5].

Memory management therefore combines protection, performance and overcommit decisions. Virtual memory provides a clean per-process model, while the kernel continuously manages physical frames, caches, writeback and reclaim underneath that model [1].

Important distinction. Virtual address space is the process-visible abstraction. Physical memory management is the kernel mechanism that supplies and reclaims the pages backing that abstraction.

File System Management Approaches

Linux presents files through the Virtual File System, or VFS. VFS defines common kernel objects and operations so the same system calls can work with ext4, XFS, FAT, network file systems and pseudo file systems. A user program therefore calls open(), read(), write() and close() without needing a separate API for each underlying file-system format [1], [6], [8].

Important VFS objects include the superblock, inode, dentry and file object. A superblock represents a mounted file system. An inode represents a file-system object and its metadata. A dentry represents a name-to-inode relationship in the directory cache. An open file object stores per-open state such as the current file position [6].

Mounting attaches a file system to a directory in the single Linux directory tree. The root file system is mounted at /, and other file systems can be attached below it. Path lookup crosses mount points transparently, which keeps the user-visible namespace uniform [1], [6].

11

7.1 On-disk file systems, caches and pseudo file systems

A disk file system maps file names and logical offsets to storage blocks and keeps metadata such as ownership, permissions, timestamps and file size. Linux file systems commonly use journaling or related consistency techniques so metadata can be recovered after a crash. ext4, for example, uses extents to describe ranges of blocks efficiently and maintains a journal for selected updates [1].

The page cache connects file-system access with memory management. Reads can be satisfied from cached pages, while buffered writes often update cached pages first and are written to storage later. This reduces device traffic and allows the kernel to combine writes. fsync and related interfaces let applications request stronger persistence when needed [1], [8].

Table 3. Common Linux file-system layers and objects
Layer / objectPurpose
VFSCommon file API and pathname framework.
SuperblockRepresents a mounted file system and its global state.
InodeStores metadata and operations for a file-system object.
DentryCaches pathname components and links names to inodes.
File objectRepresents an open instance and current access state.
Page cacheCaches file contents in memory.

Linux also uses pseudo file systems that expose kernel information rather than ordinary disk files. /proc presents process and kernel information, while sysfs exposes device and driver objects. These interfaces make many kernel properties accessible through familiar file operations, although the underlying data is generated by the kernel [6], [7].

Device Management Approaches

Linux device management separates hardware-specific code into drivers and connects those drivers to common kernel subsystems. Applications normally access character devices, block devices, network interfaces, graphics devices or other subsystem abstractions rather than programming hardware registers directly [1], [7].

↓

↓
Interrupts and DMA
↓
Hardware controller / device
Figure 6. Simplified device I/O flow

Character devices commonly provide stream-style read and write operations, while block devices support random access to fixed-size blocks and are used by storage stacks. Network drivers register interfaces with the networking subsystem. Other frameworks handle USB, PCI, input, sound and graphics. This organization lets user-space interfaces remain relatively stable while different drivers implement device-specific operations [7].

The Linux device model represents buses, devices, drivers and classes as kernel objects. sysfs exports much of this hierarchy, and user-space device management tools can react when devices are added or removed. A driver matches compatible devices, initializes hardware resources and registers the services that higher kernel layers will use [7].

13

8.1 Interrupts, DMA and I/O synchronization

Hardware often signals completion or attention with an interrupt. The kernel's interrupt handling path performs urgent work and defers longer processing so the CPU can return to normal tasks. Drivers synchronize interrupt handlers with process-context code because both may access the same device state [7].

Direct Memory Access lets a device transfer data between device buffers and main memory with less CPU copying. The driver prepares memory that is suitable for DMA, programs the device and later handles completion. Cache coherence, address translation and platform rules are handled through kernel DMA APIs rather than by assuming that a CPU virtual address is a device-visible bus address [7].

Table 4. Device I/O mechanisms
MechanismRole
Programmed I/OCPU explicitly reads or writes device registers or ports.
InterruptDevice notifies the CPU that attention or completion is required.
DMADevice transfers blocks of data to or from memory with limited CPU copying.
Buffering / queuesKernel and driver absorb rate differences and schedule requests.
Device frameworkCommon subsystem API hides hardware-specific details from upper layers.

Device management is therefore more than a collection of drivers. It is a layered system of discovery, resource allocation, synchronization, power management, interrupts, DMA and common subsystem APIs. The aim is to expose hardware safely while allowing the rest of the operating system to work with consistent abstractions [1], [7].

Chapter 9

Summary

Linux combines a monolithic privileged kernel with modular construction. Processes and threads are represented as schedulable tasks, and the scheduler selects runnable work according to scheduling class and priority. Blocking operations cooperate with the scheduler so tasks waiting for I/O or synchronization do not consume CPU time [1], [4].

IPC gives isolated processes controlled ways to exchange data. Pipes and sockets provide streams, message queues preserve message boundaries, shared memory provides high-throughput local sharing, and semaphores or mutexes coordinate concurrent access. These mechanisms connect process management directly with synchronization and wake-up behavior [1], [8].

Virtual memory separates process-visible addresses from physical frames. Demand paging, copy-on-write, the page cache and reclaim allow Linux to use RAM efficiently while enforcing access protection. The VFS provides a similar abstraction for persistent data by giving applications one file API across many file-system implementations [1], [5], [6].

Device drivers complete the path from abstract kernel services to hardware. Interrupt handling, DMA and subsystem frameworks let devices operate efficiently without exposing hardware details directly to applications [7]. Taken together, these subsystems show the central Linux design pattern: present stable abstractions to programs while using specialized kernel mechanisms to manage and share the underlying resources.

The assigned base references describe these mechanisms as parts of one operating system rather than isolated topics [1], [2]. Linux is a useful case study because the relationships are visible in real interfaces: fork and wait connect process creation and termination, blocking IPC connects communication with scheduling, mmap connects files with virtual memory, and drivers connect I/O requests to physical devices.
